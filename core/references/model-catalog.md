# Model capability catalog

Forge core (`core/model_catalog/`) owns neutral tier semantics, schema, validation, persistence, role-to-tier policy resolution, and catalog resolution. It stores the catalog at `${VAULT_PATH}/_shared/model-catalog/catalog.json`. When the canonical file is absent, core reads the legacy `${VAULT_PATH}/_shared/capability-snapshot.json` path as a read-only fallback; malformed or stale canonical data fails closed without fallback. Records have opaque identity, declared/public/passive evidence, normalized capabilities, neutral tier (`minimal`, `economy`, `standard`, `premium`), and runtime bindings. Manual snapshots remain valid until changed; system snapshots older than 24 hours are rejected. Future-dated, malformed, incompatible, or missing snapshots fail closed without probing or overwrite. Resolution is exact-tier, capability-filtered, active-binding-only, and deterministic. `inherit` returns explicitly; there is no cross-tier fallback or cost selection.

The Claude and Copilot adapters package and invoke core through their own `forge-model-catalog.sh` wrappers. Each wrapper fixes its runtime binding for resolution and coverage/onboarding checks; an explicit foreign binding is rejected, and a tier with only foreign active bindings returns `no_match`. Adapters acquire runtime data and dispatch the selected runtime model; they do not rank models or infer dispatch IDs. Run `forge-model-catalog.sh check-coverage --snapshot "${VAULT_PATH}/_shared/model-catalog/catalog.json"` to verify all four tiers for the wrapper's runtime before completing onboarding. Manual remapping can recover an expired system snapshot, but preserves other runtime records only with their system-sourced bindings inactive until that runtime is remapped; malformed or future-dated snapshots cannot be republished. Legacy `MODEL_<ROLE>` values remain readable; migration is backup, idempotent, non-destructive, and leaves unknown vendor values pending. Automated provider discovery, benchmarking, and cost inference are not required.

## Manual publication and migration

A fresh install can publish an explicit manual/runtime input with `forge-model-catalog.sh publish --input FILE`; missing metadata receives current UTC capture metadata, while all supplied records are recursively validated. No probe, network request, or billing data is used. Legacy configuration migration is available through `forge-model-catalog.sh migrate --config PATH` and writes `MODEL_TIER_<ROLE>` plus `forge-model-migration.json`; it never sources config, overwrites existing keys, deletes legacy keys, or replaces the first backup.
