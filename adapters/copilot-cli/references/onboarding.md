# Copilot CLI first-run onboarding

Load from `forge` step 0b for full first-run onboarding or for mapping-only recovery when a previously completed install lacks complete Copilot model coverage. Never update Claude Code's settings or configuration as part of Copilot onboarding.
For read-only catalog checks, substitute the literal absolute Copilot and vault
directories read from `forge.conf` into the examples below before invoking
Bash. Shell-variable executable paths may bypass saved CLI command approvals.

1. Welcome the user and explain Forge's vault, agent roles, and session workflow. Confirm the `VAULT_PATH` in Copilot's `forge.conf`; create the current project's vault directories (`decisions/` and `architecture/`) and a starter `INDEX.md` if absent. Offer the optional wellness coach through the installed wellness skill when present; complete its eight questions before marking wellness setup complete. A pre-existing shared preferences file does not imply Copilot onboarding was completed. Recommend superpowers if unavailable. Ask whether to track a different work folder or add another environment; either can be deferred.
2. **Required model mapping:** If the entry check already resolved all four Copilot tiers, skip only this subsection—not wellness, vault, or the rest of first-run onboarding. Otherwise ask for model IDs available in Copilot CLI, then load `/forge-setup-models` and run `"${COPILOT_HOME:-$HOME/.copilot}/skills/forge-setup-models/scripts/forge-setup-models.sh"` with `FORGE_RUNTIME=copilot-cli`. The user must explicitly choose one model for each tier (`minimal`, `economy`, `standard`, `premium`); the same ID may serve multiple tiers. Never auto-discover, infer a default, skip a tier, or fall back across tiers. **Ownership boundary:** Model setup only edits user-selected tier-to-model bindings in `${VAULT_PATH}/_shared/model-catalog/catalog.json`; manual choices remain valid until changed. It never writes `MODEL_TIER_<ROLE>` or legacy `MODEL_<ROLE>` keys; role-to-tier policy belongs to Forge core, and legacy config migration is a separate task.
3. If the user defers, or setup fails or required files are missing, explain the issue and leave `ONBOARDING_COMPLETE` unchanged (false remains false; previously true remains true). The next `/forge` can resume setup; existing users can rerun `/forge-setup-models` manually.
4. **Only after other steps and mapping succeed**, run `"/absolute/copilot/directory/scripts/forge-model-catalog.sh" check-coverage --snapshot "/absolute/vault/path/_shared/model-catalog/catalog.json" --binding copilot-cli`. Continue to the entry checklist only when all four active bindings resolve. Model mapping itself never changes `forge.conf`; the completion flag is handled only in the next step.
5. **Full first-run path only, after all preceding steps succeeded:** run `"/absolute/copilot/directory/scripts/forge-model-catalog.sh" finish-onboarding --snapshot "/absolute/vault/path/_shared/model-catalog/catalog.json" --binding copilot-cli --config "/absolute/copilot/directory/forge.conf"`. This checks coverage again and sets only `ONBOARDING_COMPLETE=true`, preserving every other config key. Never run it on deferral, failure, or the map-models-only path of an already-completed installation.
